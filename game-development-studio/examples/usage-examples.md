# 使用示例（usage-examples.md）

> 三个典型场景走查。示例题材均为虚构占位，实际使用时替换为用户的真实项目。

## 示例 1 · 全新立项（完整流水线，模式 A）

**用户**："我想做一款太空题材的肉鸽卡牌游戏，帮我从头规划并做出来。"

**主理人动作序列**：

1. **Phase 0 诊断**：检查工作区（发现为空 → 全新立项）。向用户确认：引擎/平台（如"网页 H5 还是 Unity？"）、评审强度（推荐 lean）、以及 2–3 个题材边界问题。产出：阶段判定 + 前提决策记录。
2. **Phase 1 概念孵化（并行）**：同时派发 `design-strategist`（概念文档 → `design/concept/concept-v1.md`）与 `art-director`（美术圣经 → `design/art-bible/art-bible-v1.md`），两条 prompt 各含七要素，红线写明题材合规边界。收产出后做一致性检查（视觉锚点 ↔ 美术圣经调性是否一致），输出汇编 + "已知风险与缓解"，请用户确认"好玩"论证。
3. **Phase 2 系统设计（串行）**：派发 `design-strategist` 拆系统（如：卡牌构筑 / 地图推进 / 资源经济 / 局外成长），产出逐系统八节 GDD + 跨系统断点清单 → `design/gdd/`。
4. **Phase 3 技术搭建（并行）**：`engineering-lead` 产架构 + ADR + 架构评审 → `docs/architecture/`；`art-director` 产可访问性分级。架构评审 PASS 后放行。
5. **Phase 4 预制作**：三成员并行出 UX 规格 / 资产规格 / Epic-Story 计划，主理人汇编首个冲刺计划；建议用户先做垂直切片验证"好不好玩"。
6. **Phase 5 制作**：按冲刺循环实现 → 烟雾测试 → 设计评审，直至核心功能齐备。
7. **Phase 6/7**：并行打磨（Playtest ≥3 轮、性能、资产审计、音频），最后发布清单 + QA 签字。

**每阶段的用户可见物**：产物清单（文件路径）+ 质量门判定 + 需拍板的决策。

## 示例 2 · 单点直调（孤立小问题，模式 B）

**用户**："帮我设计一个装备强化系统，别太肝。"

**主理人动作**：命中路由表"系统设计/经济平衡" → **不启动完整流水线**，直接派发 `design-strategist`（Task ID 如 `T-Q-ENHANCE`），prompt 附上 `deliverable-standards.md` 第 2 节（GDD 八节）作为结构要求，Output Path 指定 `design/gdd/equipment-enhance.md`。

**收尾**：主理人核对八节齐全、数值标注"待校准"、有防作弊边界后，把角色摘要与文件路径转呈用户，并提示"若要与既有系统对齐，可让我跑一次阶段诊断"。

## 示例 3 · 半路接手（已有项目，模式 A 变体）

**用户**："接手一个朋友留下的游戏项目，代码能跑但没有文档，我想继续开发。"

**主理人动作**：

1. **Phase 0 诊断**：通读 `src/`、`tests/`、现有 README，盘点缺口（典型：无 GDD、无架构文档、无测试）。产出诊断报告：所处阶段判定（如"相当于 Phase 3 缺文档"）+ 缺口清单。
2. **补文档而非重写**：与用户确认后，反向补齐——派 `engineering-lead` 依现状**追写**架构文档与 ADR（标注"追溯性 ADR"）；派 `design-strategist` 依玩法逆向梳理最小概念文档。
3. **过门再前进**：追溯文档过架构/设计评审后，从 Phase 4（或用户选定的阶段）进入正常流水线。
4. **红线**：接手阶段只读不改；任何重构/清理动作先列清单征求用户确认。

## 反模式（不要这样做）

- ❌ 主理人直接写出完整 GDD 或架构（应派发角色；确需代笔必须标注"待复核"）。
- ❌ 一次派发任务不给 Output Path，产出散落在对话里。
- ❌ 两个角色被要求互相 review 对方产出（一致性由主理人统一负责）。
- ❌ FAIL 门控未解决就开下一阶段（除非用户明确豁免并记录）。
