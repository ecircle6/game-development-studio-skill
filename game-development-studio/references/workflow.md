# 七阶段标准工作流程（workflow.md）

> 每个阶段给出：目标、参与角色与并行性、输入、交付物（含默认输出路径）、阶段切换条件。进入任何阶段前先读本文件对应节；阶段切换处必须过质量门（见 `quality-gates.md`）。

## Phase 0 · 阶段诊断（主理人独占，串行）

- **目标**：判断项目所处阶段与缺口，与用户对齐关键前提。
- **动作**：
  1. 读取项目现有产物（`design/`、`docs/`、`production/`、`src/`、`tests/`），盘点"已有什么、缺什么、质量如何"。
  2. 与用户确认三件事：引擎/技术栈方向、目标平台、评审强度（full 完整文档 / lean 轻量 / solo 快速原型）。
  3. 若为"推倒重来"，先沉淀复盘（失败原因、约束条件）再进入 Phase 1。
- **切换条件**：阶段判定 + 前提决策均获用户确认。

## Phase 1 · 概念孵化（并行 spawn）

- **目标**：回答"做什么、为什么好玩、长什么样"。
- **参与**：`design-strategist` ∥ `art-director`（互不依赖，同时派发）。
- **交付物**：
  - 概念文档（支柱、MDA 分析、核心循环、范围分层 MVP/v1/Stretch、虚构化或题材合规边界、视觉锚点）→ `design/concept/`
  - 美术圣经（视觉身份九节：调性/色彩/字体/角色/场景/UI/插画/动效/参考与红线）→ `design/art-bible/`
- **切换条件**：设计评审 PASS，且用户认可"好玩"论证。

## Phase 2 · 系统设计（串行，依赖 Phase 1）

- **目标**：把概念拆成可实现的系统规格。
- **参与**：`design-strategist`（串行三步）。
- **动作**：系统拆解与依赖排序 → 逐系统 GDD（每系统八节）→ 跨 GDD 一致性检查 + 设计理论自评。
- **交付物**：系统 GDD（含全局数值字典、系统间耦合、断点清单）→ `design/gdd/`。
- **切换条件**：一致性检查无未处理断点；用户认可系统清单与范围。

## Phase 3 · 技术搭建（并行 spawn）

- **目标**：确定技术方案并保证架构级正确性。
- **参与**：`engineering-lead` ∥ `art-director`。
- **交付物**：
  - 主架构文档（技术栈、模块划分、状态管理、系统间通信、数据模型、持久化、性能预算）+ **≥3 条基础层 ADR** + 架构评审（PASS/CONCERNS/FAIL）+ 控制清单 → `docs/architecture/`
  - 可访问性分级（Basic/Standard/Comprehensive）与特性矩阵 → `design/art-bible/accessibility-*.md`
- **切换条件**：架构评审 PASS（CONCERNS 须列出跟踪项）；用户认可技术栈。

## Phase 4 · 预制作（并行 → 汇编）

- **目标**：为首个冲刺备齐规格，锁定验证路径。
- **参与**：`design-strategist`（UX 规格）∥ `art-director`（资产规格）∥ `engineering-lead`（Epic/Story 拆分、测试框架脚手架）→ 主理人汇编。
- **交付物**：UX 规格 → `design/ux/`；资产规格 → `design/art-bible/`；切片计划 → `production/epics/`；**主理人汇编产出首个冲刺计划**。
- **推荐动作**：安排**垂直切片**（最小核心循环可玩版本）作为"好不好玩"的验证载体，再决定是否扩展全量。
- **切换条件**：三份规格齐备且互相引用一致；用户认可冲刺计划与切片范围。

## Phase 5 · 制作（按冲刺循环）

- **目标**：持续产出可玩增量。
- **每冲刺循环**：
  1. `engineering-lead` 实现就绪 Story（遵循控制清单与门禁）。
  2. `quality-lead` 产 QA 计划与烟雾测试（附证据）。
  3. `design-strategist` 做设计评审与范围检查（防止范围漂移）。
  4. 主理人收尾：一致性检查 + 回顾 + 下一冲刺计划。
- **切换条件**：进入 Phase 6 的标准——核心功能全部落地且烟雾测试通过。

## Phase 6 · 打磨（并行 spawn）

- **目标**：把"能玩"磨成"好玩、稳定、无障碍"。
- **参与**：`quality-lead`（≥3 轮 Playtest）∥ `engineering-lead`（性能剖析与优化）∥ `art-director`（资产审计）∥ `audio-director`（音频打磨）。
- **交付物**：Playtest 报告 → `tests/playtest/`；性能报告与优化清单 → `docs/`；资产审计与音频打磨报告 → `design/`。
- **切换条件**：Playtest 关键问题清零或降级豁免；性能达标；最终内容审计通过。

## Phase 7 · 发布（串行）

- **目标**：安全、可回滚地上线。
- **参与**：`release-ops-lead` → `quality-lead`。
- **交付物**：发布清单、版本号与构建产物、补丁说明、上线检查清单、本地化覆盖表、回滚预案 → `production/release/`；最终 QA 门控签字 → `tests/qa/`。
- **切换条件**：QA 签字放行 + 用户批准发布动作。

## Phase 8 · 汇编交付（主理人独占，随时触发）

- **目标**：让任何阶段的产出成为用户可掌握的资产。
- **动作**：收齐成员回传 → 跨成员一致性检查（命名/数值/事件流/红线，见 `roles.md` 主理人节）→ 向用户输出"产物清单 + 已知风险与缓解 + 下一步建议"。

## 评审强度对流程的影响

| 强度 | 文档要求 | 适用 |
|---|---|---|
| full | 全阶段全量交付物 + 全部门禁 | 正式团队/长线项目 |
| lean | 交付物精炼、门禁只保留设计/架构评审 | 快速验证与迭代 |
| solo | 以可玩原型为先，文档仅保留概念 + 控制清单 | 个人/黑客松 |
