# 质量门制度（quality-gates.md）

> 质量门设在阶段切换处。判定只有三档：**PASS / CONCERNS / FAIL**。判定必须给出具体阻塞项/跟踪项，不允许"感觉没问题"。

## 一、四类标准质量门

| 门控 | 时机 | 主评人 | 评审对象 |
|---|---|---|---|
| 设计评审 | Phase 1 → 2、各冲刺设计产物后 | 策划（主理人复核） | 概念文档、GDD、UX 规格 |
| 架构评审 | Phase 3 结束 | 工程 | 架构文档、ADR、控制清单 |
| 烟雾测试 | 每个可玩增量 / 进入 Phase 6 前 | 质量 | 核心流程可用性 |
| 发布检查 | Phase 7 放行前 | 质量（签字）+ 发布运营（清单） | 发布清单、回滚预案、QA 报告 |

## 二、判定标准

### PASS（通过）
- 所有验收项满足；无未处理的一致性断点；红线零违反。
- 可进入下一阶段。

### CONCERNS（有条件通过）
- 核心可行，但存在**非阻塞**问题。必须逐条列出：
  1. 跟踪项描述；
  2. 影响（若不处理会发生什么）；
  3. 建议处理时机（哪个阶段/哪个冲刺）。
- 处理规则：可进入下一阶段，但跟踪项必须写入后续阶段的任务清单，不得静默丢失。

### FAIL（阻塞）
- 存在以下任一情形：
  - 红线违反（合规/虚构化/版权等硬约束）；
  - 关键验收项未满足且无替代方案；
  - 系统间一致性断点未闭合（如数据双写遗漏、关键内容不可达）。
- 处理规则：**禁止进入下一阶段**。除非用户明确豁免（豁免须记录在案），否则先修复再评审。

## 三、评审输出模板

```
## <门控名称> 评审 · <日期>
判定：PASS / CONCERNS / FAIL

### 验证矩阵
| 验证项 | 结果 | 依据 |
|---|---|---|
| <项> | ✅/⚠️/❌ | <文档章节/测试名> |

### 阻塞项（FAIL 时必填）
1. <描述> — 修复责任角色：<ID> — 建议时限：<阶段/冲刺>

### 跟踪项（CONCERNS 时必填）
1. <描述> — 影响：<…> — 处理时机：<…>

### 结论与下一步
<一句话结论 + 进入/不进入下一阶段 + 用户需拍板的决策（如有）>
```

## 四、阶段切换附加要求

每次阶段切换，主理人除门控判定外，还须输出：

1. **阶段产物清单**：本阶段全部落盘文件路径一览。
2. **已知风险与缓解**：按"风险 → 影响 → 缓解措施 → 责任角色"四元组列出。
3. **需用户拍板的决策**：以 2–4 个带取舍说明的选项呈现（涉及范围、引擎、预算、题材边界等高影响项）。

## 五、失败复盘规则（推倒重来场景）

当整个方案被用户否决时：
1. 先沉淀**复盘文档**（失败根因、硬约束、既有素材），再重启 Phase 1；
2. 新概念必须显式对照失败原因逐条给出解法；
3. 复盘文档落 `design/retro/` 或项目根，作为后续所有阶段的输入。
